# GenAI Usage

## 1. Tool and workflow

- **Tool:** Claude (Anthropic) used as an agentic coding assistant with shell access to run
  tests, linters and a real PostgreSQL / Redis instance.
- **Workflow:** I did not ask for "the whole app" in one prompt. I split the work into layers
  (domain → use cases → infrastructure → API → Docker → frontend). After each step I ran the
  tests, linters and the app, and reviewed the diff before moving on.
- **My role:** I set the architecture, the authorization rules and the quality gates (TDD, 80%
  coverage, strict mypy). The AI wrote most of the first drafts, and I reviewed and corrected
  them.

## 2. Prompts

### 2.1 Main scaffold prompt

```text
You are a senior Python backend engineer. Build the backend of a task management REST API.

Stack (mandatory):
- FastAPI, SQLAlchemy 2.0 (typed Mapped[] models), Alembic, PostgreSQL (SQLite for tests)
- JWT auth with PyJWT (OAuth2 password flow so Swagger "Authorize" works), bcrypt hashing
- slowapi rate limiting, Celery + Redis for background jobs
- uv + pyproject.toml, ruff, mypy --strict, pytest + pytest-cov (fail under 80%)

Architecture (Clean Architecture, strictly enforced):
- app/domain: dataclass entities (User, Task, TaskStatus enum) and business rules.
  NO imports from FastAPI, SQLAlchemy or Pydantic.
- app/application: repository/service ports as typing.Protocol + use case classes
  (AuthService, TaskService) that depend only on ports.
- app/infrastructure: SQLAlchemy models + repositories that map ORM <-> domain entities
  (ORM objects must never leave this layer), JWT/bcrypt adapters, Celery app.
- app/api: routers, Pydantic schemas, dependency wiring, domain-error -> HTTP mapping.

Business rules:
- A task has title (1-200 chars, trimmed), description, status (pending|in_progress|completed),
  due_date (date, optional), owner_id, assignee_id (optional), completed_at.
- Owner can update/delete. Assignee can view and complete. Anyone else gets 404 (not 403).
- Completing sets completed_at; moving away from completed clears it. Completing is idempotent.
- Assigning to someone else enqueues a Celery notification; so does an assignee completing.
- PATCH must distinguish "field omitted" from "field: null" (null due_date clears it).

Endpoints under /api/v1: auth (register, login, me), users (list active), tasks
(list with pagination page/size<=100 and filters status, due_date_from, due_date_to,
assignee_id, search; create; get; patch; delete; POST /{id}/assign; POST /{id}/complete).

Testing (TDD): write the tests first.
- Unit tests for entities and use cases with in-memory fake repositories (no DB).
- API tests with TestClient + in-memory SQLite, covering auth errors, permissions,
  validation, pagination and every filter.

Do not invent library APIs. If unsure about a version-specific behaviour, say so.
Output the file tree first, then each file.
```

## 3. Representative output

Use case generated by the AI and kept after review. It is framework-free and depends on ports:

```python
@dataclass
class TaskService:
    tasks: TaskRepository
    users: UserRepository
    notifier: NotificationDispatcher

    def get_task(self, actor: User, task_id: int) -> Task:
        task = self.tasks.get_by_id(task_id)
        # 404 instead of 403 for tasks the user cannot see: don't leak existence.
        if not task or not task.is_visible_to(self._id(actor)):
            raise NotFoundError(f"Task {task_id} not found")
        return task

    def complete_task(self, actor: User, task_id: int) -> Task:
        task = self.get_task(actor, task_id)          # owner OR assignee
        if task.status is TaskStatus.COMPLETED:
            return task                                # idempotent
        task.complete()
        updated = self.tasks.update(task)
        if updated.owner_id != self._id(actor):
            self.notifier.task_completed(self._id_of(updated), updated.owner_id)
        return updated
```

## 4. How I validated the AI's suggestions

1. **Tests first and always run.** 59 tests (unit + API), 99% coverage, enforced at 80% in
   `pyproject.toml` and CI.
2. **Static analysis.** `ruff` and `mypy --strict` on every change; type errors are often the
   first sign of a hallucinated API.
3. **Running against real infrastructure, not only mocks.** I ran the API against PostgreSQL 16,
   Redis and a Celery worker and exercised it with `curl`. This found two bugs that the green
   test suite did not catch (see section 5).
4. **Migration round-trip.** `alembic upgrade head → downgrade base → upgrade head` plus
   `alembic check` (models and migration in sync).
5. **Reading the diff with a security checklist.** Password exposure, user enumeration, JWT
   algorithm pinning, authorization on every endpoint, input limits.

## 5. Corrections and improvements to the AI output

| # | Problem in AI output | How I found it | Fix |
|---|---|---|---|
| 1 | **Successful login returned HTTP 500.** With `headers_enabled=True`, slowapi needs a `response: Response` parameter in decorated endpoints. | Manual `curl` against the running server. Tests passed because the limiter was disabled. | Added the parameter, plus a test that enables the limiter, does a *successful* login and checks the `X-RateLimit-Remaining` header. |
| 2 | **19-second requests when Redis is down.** The Celery *result backend* retried the connection on the request path. | Stopped Redis and timed the request; `faulthandler` showed where it blocked. | Removed the result backend (jobs are fire-and-forget), `apply_async(retry=False)`, 2 s socket timeouts, errors logged. 19 s → 2 s, and the request still succeeds. |
| 3 | **Alembic downgrade left the PostgreSQL `ENUM` type behind**, so the next upgrade failed. | Migration round-trip test. | Explicit `sa.Enum(name="task_status").drop(...)` in `downgrade()`. |
| 4 | Suggested `passlib[bcrypt]`. | Known issue: passlib is unmaintained and breaks with bcrypt ≥ 4.1. | Used `bcrypt` directly and truncated input to 72 bytes explicitly (tested with a 200-byte UTF-8 password). |
| 5 | `CORS_ORIGINS=http://localhost:5173` in `.env.example`. | pydantic-settings parses `list[str]` as JSON, so the app would crash at start-up. | Changed it to JSON (`["http://..."]`). |
| 6 | Wrong `Select[tuple[TaskModel]]` type hint; deprecated `HTTP_422_UNPROCESSABLE_ENTITY`. | mypy and a runtime deprecation warning. | Fixed the annotation; used the literal `422`. |
| 7 | Test SQLite engines never disposed (`ResourceWarning`). | Ran pytest with `-W default`. | `engine.dispose()` in the fixture teardown. |
| 8 | Frontend: dates created with `new Date('2026-03-01')` show the previous day in UTC-4 (Bolivia). | Code review: a classic timezone bug. | Parse `YYYY-MM-DD` as a local date; added a unit test. |
| 9 | Frontend: tests using `getByText('Completed')` passed or failed by luck, because the `<option>` in the status filter has the same text. | Flaky test while running the suite. | Assert on behaviour (Complete button disappears, success message shown) instead of text. |
| 10 | Frontend: no proof that the console was clean. | The requirement explicitly asks for it. | Playwright script against the real API that logs every console warning/error, run on desktop and mobile viewports: 0 found. |

## 6. Edge cases, authentication and validation

- **Auth:** OAuth2 password flow; JWT with `exp`, `sub`, `iat` and a `type` claim; algorithms
  pinned; tokens signed with another secret, expired or malformed → 401 with `WWW-Authenticate`.
  Deactivated users are rejected even with a valid token.
- **User enumeration:** same error for unknown email and wrong password.
- **Brute force:** 5/min on login and register, 100/min globally (Redis-backed in Docker).
- **Validation:** Pydantic (email format, lengths, `size ≤ 100`, `page ≥ 1`, positive IDs) plus
  domain rules (trimmed non-empty title, assignee must exist and be active).
- **PATCH:** `null` for `title`/`status` → 422; `null` for `due_date` clears it; omitted fields
  are untouched.
- **Filters:** `due_date_from > due_date_to` → 422. Tasks without a due date go last.
- **Authorization:** non-visible task → 404 (not 403); assignee editing or deleting → 403.

## 7. Performance and idiomatic quality assessment

- **Queries:** one `COUNT` plus one paginated `SELECT` per list. No N+1 (no lazy relationships
  are accessed). Composite indexes match the filters.
- **Idiomatic Python:** dataclasses and `StrEnum` in the domain, `typing.Protocol` for ports,
  `Annotated` dependencies in FastAPI, SQLAlchemy 2.0 typed `Mapped[]`, `mypy --strict` clean.
- **What I would not accept from the AI without review:** security-related defaults (CORS,
  token expiry, secrets), anything that blocks the request path (I/O to optional services),
  and migrations, which I always run in both directions against the real database engine.

**Lesson:** a green AI-generated test suite is not enough. Two of the most important bugs only
showed up when running the system against real infrastructure and testing failure modes
(Redis down, limiter on).
